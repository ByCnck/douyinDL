## 确认：-i 文件 URL 下载顺序
- 用户要求 `-i` 解析 urls 文件后按源文件 URL 顺序下载，不要另外排序。
- 核查结论：整个 `downloader.py` 无任何 `sort`/`sorted` 调用；`run_all` 直接 `enumerate(urls)` 顺序遍历；`fetch_mix_videos` 按分页顺序 `extend` 收集、无排序；`run` 按返回列表顺序下载。
- 唯一与顺序相关的是 main() 中 1393-1404 的解析+去重。原实现用 `seen=set()` + 遍历有序列表 append，已保序；本次改为 `urls = list(dict.fromkeys(urls))`（Python 官方保序去重惯用法），并加注释强调「禁止排序」，固化意图、防回归。
- 验证：`py_compile` 通过；复刻逻辑测 5 条含重复用例，输出严格按源文件顺序、重复项停留原位，总条数正确。

## 修复：f2 gen_real_msToken 端点 503 导致程序起不来
- 现象：运行 `-i urls` 时打印 `gen_real_msToken` 内 `httpx.HTTPStatusError: 503 (mssdk.bytedance.com/web/report)`，本次因导入期端点恰好 200 拿到缓存 token 故未崩、仅跳过。
- 根因：f2 在 `model.py` 的 `BaseRequestModel.msToken` 类属性于「模块导入期」直接调用 `TokenManager.gen_real_msToken()`，请求外部端点偶发 503；f2 自带 try/except 的 except 又二次调用同一失败函数，端点持续 503 时模块导入失败、整个 downloader.py 起不来（用「强制 gen_real_msToken 抛异常」模拟复现确认导入期崩溃）。
- 端点实测当前 HTTP 200，属偶发故障，须兜底。
- 修复：在 `downloader.py` 顶部导入 crawler/model 之前，monkeypatch `TokenManager.gen_real_msToken` 为 `_safe_gen_real_msToken`（捕获原函数，异常时回退 `gen_false_msToken()`）。utils.py 不依赖 model 故可先导入打补丁再导入 crawler/model。不改动 site-packages，uv sync 后生效。
- 验证：模拟端点持续 503 后 `import douyindl.downloader` 成功不崩，`fetch_one_video` 仍成功返回视频+播放地址；正常路径端点 200 走真实 token 无回归；py_compile 通过。
- 同步：CLAUDE.md「关键坑点」新增该条 + 升级 f2 注意点。
